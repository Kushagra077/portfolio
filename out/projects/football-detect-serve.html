Case study / CV SERVING PIPELINE

football-detect-serve

A YOLO26 football detector taken from checkpoint to endpoint: trained on SoccerNet broadcast footage, exported to ONNX, and served as four presets (test mAP50-95 0.400 to 0.477) behind a batching FastAPI service. One evaluator scores every backend, so the ONNX, INT8 and batching results are measured on the same code path, including the ones that did not pay off.

ONNX fp32 on CPU (Apple M2, 4 threads), real 1080p frames. A request picks a preset with ?backend=fast|balanced|accurate|max. The ball is the hardest class at every size (AP 0.111 to 0.199).

How it works

01

Data & train

SoccerNet MOT tracking labels are converted to YOLO format: 34,500 train, 8,250 val and 36,750 test images, with classes ball, goalkeeper, player, referee and a minor "other" that is excluded from the headline mean. Val is every 5th training sequence, so it shares matches with train and reads high; test is 3 unseen matches. Runs v1 to v13 covered YOLO26 nano at 640, 960 and 1280 px and small at 1280. Input size and model size moved accuracy; a ball-weighted loss, a P2 head and tiled inference did not.

02

Evaluate (gate)

scripts/eval_map.py computes COCO-style mAP50-95 for torch and ONNX through the same backend interface. The fp32 ONNX files match torch to three decimals per class. Cross-checked against ultralytics YOLO.val() on v3, the evaluator reads 0.015 to 0.019 higher, so model-to-model comparisons hold better than absolute values. On test, ball AP rises from 0.111 (fast) to 0.199 (max) and stays the weakest class.

03

Export ONNX

Checkpoints export to ONNX (opset 12, dynamic batch, simplified) with a .meta.json sidecar that records each model’s input size. Both backends decode through ultralytics predict(), because v3 exports an NMS-free [batch, 300, 6] output and the others a dense [batch, 9, anchors] one. A hand-written decoder produced garbage on the layout it did not expect and was removed. fp32 ONNX runs 1.5x torch on an M2 CPU (16.3 vs 24.9 ms p50) at no accuracy cost.

04

Quantize INT8 (measured)

Static INT8 shrinks v3 from 10.98 MB to 2.94 MB but costs 0.027 to 0.064 mAP50-95 on val (v6: -0.046). It was also slower than fp32 on the M2 (19.0 vs 16.3 ms) and on an x86 CI runner (57.7 vs 29.8 ms), which ruled out the first guess of ARM kernel tuning. v6’s calibration used 345 images stratified across 46 sequences; v1 to v3 predate that fix. INT8 is not served.

05

Serve (batched)

FastAPI loads all four ONNX presets and picks one per request with ?backend=. It exposes /predict, /healthz and Prometheus /metrics, applies an SSRF guard to image_url, and returns 503 when the 256-slot queue overflows. A per-backend worker batches up to 8 requests within a 15 ms window. A Locust test against v3 in local Docker shows batching losing at concurrency 1 (14.6 vs 21.5 RPS) and winning at 16 (31.0 vs 25.8 RPS). A Gradio app on a Hugging Face ZeroGPU Space is the public demo, and its speeds do not match the CPU tables.

Engineering highlights

Input size and model size were the levers: test mAP50-95 went from 0.400 (v3, 640 px) to 0.477 (v13 small, 1280 px) while latency went from 16 ms to 177 ms. Ball AP is still the weakest class at 0.199

INT8 negative result, checked on two CPUs: slower than fp32 on Apple M2 and on x86, and -0.03 to -0.06 mAP. The model is not served in INT8 and the README says why

Load testing caught an unsynchronized call into a non-thread-safe model on the no-batching path and led to a per-backend predict lock. It also showed batching only helps at high concurrency
